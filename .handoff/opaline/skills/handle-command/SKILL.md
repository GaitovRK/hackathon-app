Use the GitHub MCP tools or `gh api` REST (GraphQL is blocked, see CLAUDE.md).

## 1. Is this a command? (exit fast if not)
Act only if ALL are true, otherwise print `command: ignored` and stop:
- The comment author is the repo owner `GaitovRK`.
- The comment does NOT contain the agent footer `Generated by` + `Claude Code` (e.g. "_Generated by [Claude Code](https://claude.ai/code)_"); agents post as the owner, so never react to agent comments.
- A line of the comment starts with one of the commands below.

## 2. Discuss first (the owner's comment is a suggestion, not an order)
Read `.claude/agents/<agent>.md` and its skills, the **Decisions issue #95**, the issue/PR and the whole thread. If the suggestion touches a recorded decision, say so. Then judge the suggestion honestly: does it help sellers (faster to a usable photo, better image quality, clearer pricing, coming back for the next collection), does it fit CLAUDE.md rule 4 (revenue within App Store rules and the per-image margin), what does it cost (dev time, fal cost), what are the risks, is there a better option? Use data (read-only DB, PostHog), code, marketing-agents findings and research where useful.

Then decide:
- **It works** (you agree, maybe with small tweaks you name) → say so and make the change (step 3).
- **It doesn't work, or only partly** → explain why in plain words, propose the best alternative, and change nothing. Wait for the owner's reply.
- **The owner explicitly says to implement** ("implement", "do it", "go ahead", "apply") → make the change even if you disagreed, after noting your concern in one line. App Store / consumer-law limits in CLAUDE.md rule 4 and the migration rule 9 still win: then offer the closest allowed version instead.

## 3. Making the change (only when step 2 says so)
| command | agent file | change |
|---|---|---|
| `/product` | product.md | Revise the issue spec (keep "Original note" at the bottom), then `agent:dev` (or `agent:design`) + `status:todo`. |
| `/design` | designer.md | Revise the issue's `## Design` section per the `design-spec` skill, then `agent:dev` + `status:todo`. |
| `/dev` | developer.md | Issue: implement (branch, tests, `pnpm verify`, reviewer, PR). PR: change the PR branch, push, `pnpm verify` (+ `pnpm verify:mobile`). Run the cloud setup from `ops/routines.md` first if deps are missing. |
| `/analyst` | data-analyst.md | Answer with numbers and the query used (nothing to change). |
| `/manager` | manager.md | Re-route / re-label. |
| `/qa` | qa.md | Re-review the PR and update the QA comment. |

## 4. Record the outcome
If the owner agreed with you, or told you to implement, or rejected an idea, append one line to #95's body (see CLAUDE.md "Decisions"). Skip it for small details that only matter to this issue.

## 5. Reply (always, once)
On the same issue/PR:
- **Verdict:** good to implement / not recommended / partly — one line.
- **Why:** 2–4 bullets (seller impact, evidence, cost, risks).
- **Alternative** (if not recommended).
- **Done:** what you changed with links, or "No changes made — reply 'implement' if you still want it."
Never start a line of your reply with a slash command. Never merge, publish, grant credits or spend money.
